# 兼容边界

**稳定安装请选择 1.8.2。** [1.8.2 发布包的兼容清单](https://github.com/pler1y/hermes-telegram-ux/blob/v1.8.2/plugin/compatibility.json)支持下面前四套核心基线；README 与原生安装指南固定安装这个版本。

当前开发分支为 **1.8.3-rc.2 Full 候选**，沿用 1.8.3-rc.1 的五套核心基线，尚未发布。本轮验证见 [Full 维护进度](FULL-PROGRESS.md)。不要把候选新增的支持范围用于判断 1.8.2 是否兼容。

| Hermes | 核心提交 | 1.8.2 稳定版 | 1.8.3-rc.1 候选的验证范围 |
|---|---|---|---|
| 0.21.0 | `b499ab11fe8b081470e269f2fb27abae03000da5` | 支持 | 回归、原生安装、注册及两种 ZIP 的生命周期 |
| 0.21.2 | `a84a2223f82c3d9906fd4a9d778a188774e7a08e` | 支持 | 上述检查及官方 catalog admission validator |
| 0.21.2 | `436ec489854b7110b4c5506b1f52c514fa4c3ace` | 支持 | 上述检查；另验证上游任务租约、停止及替换任务的回归 |
| 0.21.2 | `044a77b3b6af4ce16138d42762f812a20b9f7a89` | 支持 | 上述检查；审查失败回合持久化和恢复变更 |
| 0.21.2 | `5eb99eb2844b22ebb723711b8e6a0bbb80bb5f04` | 不支持 | 2026-09-14 固定的官方 main；原生 install/validate/enable、未配置加载、声明负例及回归，见 [候选验证](VALIDATION-1.8.3-rc.1.md) |

表中验证范围记录 1.8.3-rc.1 的历史基线；以下源码保护继续用于当前 Full 候选；稳定版的实现边界见 [v1.8.2 文档](https://github.com/pler1y/hermes-telegram-ux/blob/v1.8.2/docs/COMPATIBILITY.md)。

`plugin/compatibility.json` 为每套基线记录 23 个文件的原始 SHA-256 和完整 Python 语法树指纹。原始字节不同时，只有完整语法树仍与同一基线一致才接受，并在 `format_only_files` 中列出。注释、空白、换行格式和不改变语法树的排版可以变化；作用域、表达式、字面量值、默认值、装饰器和 docstring 仍受检查。检查过程只解析源码，不导入或执行待检查代码；各基线仍不能混搭。

这不是对任意 0.21.x 提交的支持承诺。实际语法树变化仍需检查差异并运行回归。CI 对 Python 3.11 和 3.12 执行真实核心副本检查：追加注释应通过，追加可执行语句应拒绝。每次 push/PR/手动运行会检查当时的官方 main，没有自动接纳未知核心的开关。


兼容策略为 `reviewed-source`（schema 4）：基线清单必须非空，每套基线必须完整提供统一的 23 个文件及 AST 指纹，不允许缺项、混搭或重复提交。源码匹配后，再读取 core 的 `pyproject.toml`，要求版本与该基线完全相同；相同接口不自动授权新的 Hermes 版本。源码归档无需 Git；Git HEAD 仅用于诊断。

自有 ZIP 安装和原生配置助手在写入前检查兼容性。官方 Git install 只负责落盘，enable 只改启用状态；真正运行时的保护位于 `register(ctx)`，在导入 UX runtime、注册能力或接线前执行。未知核心可能已经安装／启用，但 validate 和加载会拒绝；不会先打上一半补丁。检查器不在插件发现线程导入 `gateway.run`，避免发现锁与网关导入相互等待。

公开接口包括 tools、hooks、middleware、系统提示区块和 Telegram platform handler。内部适配涉及消息入口、回合前及回合中的上下文压缩、长任务通知、忙碌输入回执、停止、后台完成消费、Telegram 发送与编辑、部分显示清理。内部接口没有跨任意版本的稳定保证。

运行期不修改 Hermes 源码文件。关闭插件并重启进程后，这些运行期适配消失。已验证后来增加的包装在卸载时被保留，本插件被其引用的旧包装会转发到原行为；继承的方法恢复为继承关系。加载中途失败会回滚当前加载的处理器及包装，同一应用的重复接线不会增加重复处理器。这些检查不代表与所有第三方插件组合都兼容。

Schema 中的 `_hermes_progress` 是展示元数据，在实际工具 hooks、审批和执行前移除。只对已支持的 OpenAI / Codex 简单参数结构启用 strict 转换；其他提供方保留原生结构并增加公开说明字段。可选参数的空占位会恢复为省略，原本合法的 null 保留。

提供固定中英文界面；模型生成内容通过所选语言的提示规范引导。群聊、话题与身份隔离有回归覆盖。此前完整实机记录来自 1.7.0 的私人聊天；本版本在新核心上的自动测试不等于新的 Telegram 实机验收，目前未声称在该核心上完成新的全流程实机验收。

官方原生 Git 安装及配置入口见 [NATIVE-INSTALL.md](NATIVE-INSTALL.md)。ZIP 管理与原生管理不能在同一安装记录上混用。

上游参考：[原生插件开发文档](https://hermes-agent.nousresearch.com/docs/developer-guide/plugins/)。安装行为以这里固定的核心源码和本项目测试结果为准，不把上游未来变化当作已兼容。

## 维护与升级策略

目录条目的 `>=0.21.0,<0.22.0` 只是外层筛选，实际支持以上完整基线及同版本、同完整 AST 的源码。保留整文件检查，当前不采用仅检查方法名/签名、静默降级、validator 特例或允许未知版本的开关。代价是上游可执行改动需要新候选；这一维护成本明确对外公布。

新增支持时先固定完整 core SHA，与最近基线逐项比较受保护文件和其新委托路径；确认授权、停止、任务归属、批处理和发送语义。使用 Python 3.11 生成 `python_ast_v1` 指纹，在 3.11/3.12 校验，然后运行全部插件回归、受影响的上游测试及原生生命周期。审查和检查完成后才能把整套新基线放入发布包、CI 矩阵与本表，禁止仅刷新哈希。

CI 在 push/PR/手动运行时检查官方 main；不匹配即失败，不会自动放行。匹配后还必须运行官方 validate 及未配置的原生 enable/discovery。发布和目录 pin 审阅前需针对当时 upstream 再验证；保留已支持版本供用户在核心升级前检查，失败时保持原生 Hermes 行为或回到受支持核心。

原生插件 manifest 保持不写 `requires_hermes`，因为三套旧的 0.21.2 验证器从错误的模块导入版本解析函数。2026-09-14 核心已修复该问题，但加入此字段会让旧验证器回归失败。外层约束写在目录条目，版本检查和完整源码保护由所有路径共用的插件 guard 强制执行。
